# 功能开发实录（26.3 渲染 + 动态照明）

本文档记录从 1.21.11 升到 26.3 后，新开发三个特性的经验，重点是 **26.3 渲染系统重构带来的 API 变迁**，以及 **DynamicLights（动态照明）从 0 到可用踩过的所有坑**。供后续开发参考。

---

## 一、设计理念（沉淀自用户反馈）

这些是本次开发中用户反复强调的偏好，后续新增功能务必遵守：

1. **简洁实用，开关少而精**：一个功能对应一个配置开关，不要堆砌。HUD 信息类功能尤其要克制——「够用即可」，不要塞一堆坐标/时间/朝向等数据（本次就删掉了 Simple HUD Enhanced 那套 6 行 HUD，只留图腾计数一个点）。
2. **先参考原版模组源码，再动手**：移植一个功能前，先去 Modrinth 拿 GitHub 地址、读它的实现，而不是凭空造轮子。本次三个特性都先查了参考仓库（见第七节）。
3. **效果要对齐原版**：位置、统计口径、显示方式都以参考模组为准（图腾数量按 TotemCounter 的「经验条上方 38px，有等级再上移 6」算法）。
4. **工具要跨平台**：能用一个跨平台脚本（Python）解决的事，不用 PowerShell 这种只跑 Windows 的。
5. **已内置的功能从 mod-list 移除**：`mods/mod-list.txt` 是「还需要下载的模组」清单，功能一旦自研实现，就要把对应模组从清单删掉，并在注释区标注「已内置（对应配置项）」。

## 二、26.3 渲染系统关键变化（API 变迁速查）

26.3 对渲染层做了大重构，很多 1.21.x 时代的 API 直接消失，这是本次最大的坑。

| 旧（≤1.21.x） | 新（26.3） | 说明 |
|---|---|---|
| `RenderType.translucent()` | `RenderPipelines.TRANSLUCENT_BLOCK` 等 | `RenderType` 类被移除，改用 `RenderPipeline` |
| `BlockRenderLayerMap.putFluid(...)` | **已移除**（Fabric API 27.0.14 中该类不存在） | I See Lava 的旧实现方式彻底不可用 |
| 流体渲染层由 `BlockRenderLayerMap` 控制 | 由 `FluidModel.layer()` 返回 `ChunkSectionLayer`（`SOLID`/`CUTOUT`/`TRANSLUCENT`）决定 | 岩浆透明需 Mixin `FluidModel.layer()` |
| 方块光照入口 `LightmapTextureManager` | `LightCoordsUtil.getLightCoords(...)` | 方块渲染最终都走这里取光照贴图坐标 |
| 光照贴图 `packedBrightness`（`BrightnessGetter.DEFAULT` 的 lambda） | 仍在，但只被 `Display`/`BrushableBlockRenderer` 等少数类直接引用 | 方块渲染走的是上层 `getLightCoords` |
| 光照实时更新 | **光照烘焙进 chunk mesh，需 `LevelExtractor.setSectionDirty*` 触发重建** | 这是动态照明「不跟随」的根因 |

**核心结论**：26.3 里方块光照是**烘焙式**的，不是每帧从全局光照贴图采样的。任何要「随实体移动实时变化」的光照，都必须配套 chunk 重建调度。

## 三、三个特性的实现要点

### 3.1 StackRefill（物品补货）—— 最简单

- 位置：`mixin/entity/PlayerStackRefillMixin.java`
- 机制：Mixin `Player.tick`，手持物品用完（空）时从背包找同种物品补到手上
- 关键 API：`Inventory.findSlotMatchingItem(stack)`、`Player.setItemInHand(Hand, stack)`
- 配置：`defaultModuleConfig.enableStackRefill`
- 注意：切槽时要重置状态，否则会把「刚补到手上」误判为「又用完了」导致反复补。

### 3.2 I See Lava（岩浆半透明）—— 已废弃

- 原版实现极简：`BlockRenderLayerMap.putFluid(LAVA, translucent)` 两行搞定。
- 但 26.3 里 `BlockRenderLayerMap` 被移除，需改用 Mixin `FluidModel.layer()`（判断纹理名含 `lava` 则返回 `ChunkSectionLayer.TRANSLUCENT`）。
- **最终废弃原因**：与项目已有的 `fluidVisible`（`BackgroundRendererMixin` 里同时处理水/岩浆雾效）功能重叠，用户要求删除。
- **教训**：动手前先确认项目里是否已有类似功能，避免重复造轮子。

### 3.3 DynamicLights（动态照明）—— 重点，见第四节

- 位置：`client/DynamicLightHandler.java`（光源追踪 + 调度）+ `mixin/render/LightCoordsUtilMixin.java`（光照注入）
- 核心机制（参考 LambDynamicLights，大幅简化）：

```
每客户端 tick：
  1. 遍历 level.entitiesForRendering()，筛选 LivingEntity
  2. 手持发光物（火把/灯笼/萤石等）→ 记录光源（位置 + 亮度）
  3. 把光源「亮度半径」内的区块 section 用 setSectionRangeDirty 标记为脏 → 触发重建
  4. 对比 lastRanges，把「消失（切换非发光物/离开）或移动」的旧范围也标记为脏 → 清除旧光照
  5. volatile 快照整体替换，供渲染线程读取

渲染时（光照注入）：
  LightCoordsUtil.getLightCoords 返回前，用 getDynamicLightLevel(pos) 叠加动态光到 block light
```

- 发光物亮度用硬编码 `Map<Item, Integer>`（火把 14、灯笼 15、萤石 15、红石火把 7……与原版方块光照等级一致），不做数据驱动。
- 距离衰减：`luminance - 欧氏距离`，线性衰减，取所有光源最大值，clamp 到 [0,15]。

## 四、DynamicLights 排查全记录（踩坑 → 解决）

这是本次耗时最久的特性，按「现象 → 根因 → 修复」记录，每个坑都是真实踩过并定位到的。

### 坑 1：注入 lambda 方法不生效

- **现象**：Mixin `LightCoordsUtil$BrightnessGetter.lambda$static$0`（`packedBrightness` 的 lambda 实现），编译、启动都通过，但动态光完全没生效。
- **根因**：lambda 方法通过 `invokedynamic` 绑定到 `DEFAULT`，方法体可能被内联，标准 `@Inject` 注入的是「死代码」。（LambDynamicLights 用的是 mixinextras 的 `@ModifyReturnValue`，机制不同。）
- **修复**：换注入点到上层普通静态方法 `LightCoordsUtil.getLightCoords(...)`，标准 `@Inject` 必定生效。

### 坑 2：`@Inject` 重载方法 descriptor 不匹配

- **现象**：崩溃 `Invalid descriptor ... Expected (BlockAndLightGetter, BlockPos, ...)V but found (BrightnessGetter, BlockAndLightGetter, BlockState, BlockPos, ...)V`。
- **根因**：`getLightCoords` 有 2 参数和 4 参数两个重载，`@Inject(method = "getLightCoords")` 默认匹配到了 2 参数版，而回调是 4 参数签名。
- **修复**：用完整方法签名精确匹配 4 参数版：
  ```java
  @Inject(
      method = "getLightCoords(Lnet/minecraft/util/LightCoordsUtil$BrightnessGetter;Lnet/minecraft/world/level/BlockAndLightGetter;Lnet/minecraft/world/level/block/state/BlockState;Lnet/minecraft/core/BlockPos;)I",
      at = @At("RETURN"), cancellable = true)
  ```

### 坑 3：`block`/`withBlock` 光照单位弄错

- **现象**：修复注入点后数值看似对，但视觉没亮。
- **根因**：`LightCoordsUtil.block(lightmap)` 返回的是 **0-15** 的光照等级，`withBlock(lightmap, level)` 也期望 **0-15**。我一开始写成了 `(int)(dynamicLight * 16.0)`，放大 16 倍又左移，数值完全错乱。
- **修复**：`int dynamicBlock = (int) dynamicLight;`（动态光本身就是 0-15 的 double，直接取整）。

### 坑 4：ArrayList 并发崩溃（NPE）

- **现象**：进世界后崩溃 `NullPointerException: Cannot invoke ... getLightLevel(...) because "source" is null`。
- **根因**：`LIGHT_SOURCES` 是普通 `ArrayList`，tick 线程 `clear()`+`add()`，渲染线程同时遍历，`clear()` 把元素置 null 但 size 未同步，渲染线程遍历到 null。
- **修复**：改用 **volatile 快照**——tick 线程构建好新列表后整体替换，渲染线程读到的永远是稳定快照：
  ```java
  private static volatile List<LightSource> lightSources = List.of();
  // update 里：先构建 newSources，最后 lightSources = newSources;
  ```

### 坑 5：光照不随实体移动（最隐蔽）

- **现象**：数值正确（`before=0 → after=96` 确实修改了 lightmap），但视觉没亮 / 只在进入世界那一刻生成一次。
- **根因**：26.3 方块光照是**烘焙进 chunk mesh** 的，`getLightCoords` 只在 chunk 构建时被调用。注入改了返回值，但 chunk 不重建，渲染结果不变。
- **修复**：引入 chunk 重建——`Minecraft.levelExtractor.setSectionRangeDirty(...)` 标记区块脏，触发重新烘焙。这是 LambDynamicLights 里 `ChunkRebuildScheduler` 的核心思路。

### 坑 6：旧光照残留

- **现象**：① 手持火把切到斧头，周围还是亮的；② 走到别的区块，原区块还是亮的。
- **根因**：只标记了「当前光源范围」为脏，没标记「消失/移动」后的旧范围，旧光照没被重新烘焙清除。
- **修复**：用 `Map<Integer, LightRange>`（`lastRanges`）跟踪每个发光实体上一 tick 的影响范围，每 tick 对比：
  - 当前范围 → 标记脏（实时跟随）
  - 上一 tick 有、这一 tick 消失（切非发光物/离开）或范围变化（移动）→ 把旧范围也标记脏（清除）

### 坑 7：「跨区块才更新」时效性太低

- **现象**：用户反馈「一个区块一个区块计算光照，时效性太低」——生物在区块内移动时光照不动。
- **根因**：最早实现只在「跨越 section 边界」才触发重建。
- **修复**：改为**每 tick** 都把光源「亮度半径」内的区块标记为脏（`setSectionRangeDirty(minX,minY,minZ,maxX,maxY,maxZ)`），生物每移动一格光照就刷新一格。
- **代价**：生物移动时周围区块持续重建。若后续掉帧明显，可参考 LambDynamicLights 的「剔除调度器」（只重建视锥内、光照值确实变化的区块）做优化。

## 五、Mixin 经验补充

1. **Mixin 到接口**：目标类是 `interface` 时，Mixin 类也必须是 `interface`，且注入方法必须是 **`private static`**。
   - 写 `class` 会报 `@Mixin target type mismatch: X is an interface`
   - 写 `interface` 但方法是非私有 `static` 会报 `contains non-private static method`
2. **注入重载方法**：`@Inject(method = "foo")` 默认匹配第一个同名方法，若有重载需用完整签名（含 descriptor）精确匹配。
3. 经验法则：能注入**普通静态方法**就别注入 lambda/`invokedynamic` 生成的方法，后者可能被内联导致注入不生效。

## 六、Python 脚本跨平台坑（update-mods.py）

1. **BOM**：`mod-list.txt` 由 PowerShell `Set-Content` 生成，是带 BOM 的 UTF-8。Python 读取要用 `encoding="utf-8-sig"` 自动剥离，否则 BOM 会混进第一个 slug。
2. **Windows 控制台 GBK**：`print` 中文/特殊字符会 `UnicodeEncodeError`，脚本开头强制：
   ```python
   sys.stdout.reconfigure(encoding="utf-8", errors="replace")
   ```
3. 用标准库 `urllib` / `json` 即可，零第三方依赖，跨 Windows/Linux/macOS。
